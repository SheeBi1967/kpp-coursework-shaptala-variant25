# Інформаційна система погодження внутрішніх документів

Курсова робота з дисципліни «Кросплатформене програмування», варіант 25.

Виконавець: Шаптала Максим Олександрович, група 203-ТН, Національний університет «Полтавська політехніка імені Юрія Кондратюка».

## Призначення

Система веде облік внутрішніх документів закладу, їхніх авторів і рецензентів та проводить запити на погодження через життєвий цикл
`DRAFT → SUBMITTED → REVIEW → APPROVED`. Для кожного запиту сервер обчислює інтегральний показник пріоритету

```
I = 0,40 · F1 + 0,35 · F2 + 0,25 · F3
```

- F1 — терміновість: 100, якщо строк погодження вже минув; 0, якщо до нього 30 днів і більше; інакше (30 − d) / 30 · 100, де d — кількість днів до строку.
- F2 — критичність документа: (критичність − 1) / 4 · 100, критичність у межах 1..5.
- F3 — кількість залежних процесів: min(n, 10) / 10 · 100.

Показник округлюється до двох знаків і рахується лише на сервері.

## Технології

- Java 21, Maven
- Сервер: Servlet API 4.0.1 (Apache Tomcat 9), JDBC, MySQL 8, Jackson 2.18.2, збірка у WAR
- Клієнт: JavaFX 21.0.2, `java.net.http.HttpClient`, Jackson, `java.util.logging`
- Тести: JUnit 5.11.4, maven-surefire-plugin 3.5.2

## Архітектура

```
JavaFX → HttpApprovalClient → HTTP/JSON → Servlet → Service → DAO → JDBC → MySQL
```

Клієнт не працює з базою даних напряму. Усі правила предметної області (валідація, дозволені переходи станів, обчислення I) виконує сервер.

## Структура репозиторію

## Підготовка бази даних

1. Встановіть MySQL 8 і виконайте скрипт `database.sql` від імені адміністратора (наприклад, у MySQL Workbench: File → Open SQL Script → Execute). Скрипт видаляє базу `document_approval`, якщо вона є, і створює її заново з таблицями `author`, `reviewer`, `document`, `approval_request` та тестовими даними.
2. Створіть окремого користувача для застосунку, підставивши власний пароль:

```
CREATE USER 'kpp_app'@'localhost' IDENTIFIED BY '<ваш_пароль>';
GRANT SELECT, INSERT, UPDATE, DELETE ON document_approval.* TO 'kpp_app'@'localhost';
```

3. Перевірте схему командою `SHOW TABLES FROM document_approval;`. Мають бути чотири таблиці: `author`, `reviewer`, `document`, `approval_request`.

4. Задайте для сервера змінні середовища. Пароль у коді та в репозиторії не зберігається.

| Змінна | Значення за замовчуванням | Призначення |
|---|---|---|
| `DB_URL` | `jdbc:mysql://localhost:3306/document_approval` | адреса бази даних |
| `DB_USER` | `root` | користувач бази даних |
| `DB_PASSWORD` | порожній рядок | пароль користувача |

Для Tomcat на Windows зручно створити файл `C:\tomcat9\bin\setenv.bat`:

```
set DB_USER=kpp_app
set DB_PASSWORD=<ваш_пароль>
set JAVA_HOME=C:\Program Files\Java\jdk-21
```

Файл `setenv.bat` лежить поза репозиторієм і не комітиться.

## Сервер: тести, збірка, запуск

Усі команди виконуються в папці `server`.

```
mvn clean test
mvn clean package
```

`mvn clean test` запускає 27 модульних тестів JUnit 5 із каталогу `server/src/test/java`. Для них не потрібні Tomcat, JavaFX і MySQL. Тести перевіряють:

- `PriorityCalculatorTest` (12) — фактори F1, F2, F3 та інтегральний показник I;
- `ApprovalLifecycleTest` (7) — дозволені й заборонені переходи між станами запиту;
- `EntityValidationTest` (8) — обов'язкові поля, формат дати, діапазони значень.

`mvn clean package` збирає `server/target/document-approval-server.war`.

Розгортання:

1. Скопіюйте WAR у `C:\tomcat9\webapps`.
2. Запустіть Tomcat: у папці `C:\tomcat9\bin` виконайте `catalina.bat run`.
3. Дочекайтеся рядка `Server startup` без помилок розгортання.
4. Відкрийте в браузері `http://localhost:8080/document-approval-server/authors`. Має повернутися JSON зі списком авторів; це також підтверджує, що сервер бачить MySQL.

## HTTP API

Базова адреса: `http://localhost:8080/document-approval-server`.

| Ресурс | GET | POST (параметр `action`) |
|---|---|---|
| `/authors` | список авторів | `add`, `update`, `delete` |
| `/reviewers` | список рецензентів | `add`, `update`, `delete` |
| `/documents` | список документів | `add`, `update`, `delete` |
| `/requests` | список запитів на погодження | `add`, `update`, `transition`, `delete` |

Відповіді мають формат JSON. Порушення правил предметної області або цілісності даних повертаються зі статусом 400 і тілом `{"error":"…"}`, внутрішні помилки сервера — зі статусом 500.

## Клієнт: збірка і запуск

Перед запуском мають працювати MySQL і Tomcat з розгорнутим WAR: клієнт не працює без сервера. Якщо програма показує «Сервер недоступний» або помилку 404, спершу перевірте адресу з розділу про сервер у браузері.

Клієнт потрібно запускати з папки `client`, бо шлях до CSV-файла задано відносно неї.

```
mvn clean compile
mvn javafx:run
```

Вікно програми має чотири вкладки: «Автори», «Рецензенти», «Документи», «Запити на погодження». На вкладці «Документи» розташована кнопка «Імпорт CSV» з індикатором прогресу та рядком стану.

## Імпорт документів із CSV

Імпорт виконується у фоновому потоці (`javafx.concurrent.Task`), тому вікно не блокується. Файл читається за шляхом `client/sample-data/documents.csv`.

Формат: UTF-8, роздільник `;`, перший рядок — заголовок із семи полів:

```
author_id;reg_number;title;doc_type;due_date;criticality;dependent_processes
```

Рядки обробляються послідовно, кожен документ додається через той самий HTTP-клієнт, що й решта вікон програми. Перевірки предметної області й запис у MySQL виконує сервер.

Поведінка при помилках:

| Ситуація | Результат |
|---|---|
| файл не знайдено, не читається, порожній або не в UTF-8 | імпорт не починається, показується повідомлення про помилку |
| некоректний заголовок | імпорт не починається, показується повідомлення про помилку |
| неправильна кількість полів, нечислове значення, порожнє обов'язкове поле | рядок пропускається, імпорт триває |
| сервер відхилив запис (статус 400): неіснуючий автор, повторний `reg_number`, некоректна дата, критичність поза межами 1..5 | рядок пропускається, імпорт триває |
| сервер недоступний або внутрішня помилка сервера | імпорт зупиняється з повідомленням «Імпорт зупинено на рядку N (імпортовано до зупинки: K)» |

Після завершення таблиця документів оновлюється, а в рядку стану показується «Імпортовано: N, пропущено: M». Якщо були пропущені рядки, додатково відкривається вікно з причинами (до 10 перших). Повторний імпорт того самого файла не створює дублікатів: реєстраційний номер унікальний, тому всі рядки буде пропущено.

Кнопка «Імпорт CSV» недоступна, поки імпорт виконується.

Для перевірки помилок у `client/sample-data/invalid/` лежать готові файли: `bad-field-count.csv`, `bad-number.csv`, `unknown-author.csv`, `bad-header.csv`. Щоб випробувати один із них, скопіюйте його поверх `client/sample-data/documents.csv`, а після перевірки поверніть оригінал командою `git checkout -- client/sample-data/documents.csv`.

## Журнал клієнта

Клієнт веде журнал у файлі `client/logs/client.log` (UTF-8). У ньому фіксуються початок і завершення імпорту, кількість успішних записів, пропущені рядки з причинами та помилки. Паролі й токени в журнал не потрапляють. Папка `logs/` не додається до репозиторію.

## Що не потрапляє до репозиторію

Файл `.gitignore` виключає `target/`, `*.war`, `*.log`, `*.lck`, `logs/`, `.idea/`, `*.iml`, `out/`, `.env` і `application-local.properties`. Паролі та інші секрети в репозиторії не зберігаються.
